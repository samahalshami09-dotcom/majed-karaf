# نظام ماجد كرف العقاري — المخطط الكامل (Blueprint)

**من منظومة CRM إلى نظام عقاري ذكي للمطابقة والمتابعة وإدارة المخزون**
Innova Smart Solutions — مشروع أتمتة العميل: ماجد كرف
النسخة: المخطط المرجعي الموحّد — يُبنى بالكامل على HighLevel + محرّك حسابي على Cloudflare

---

## 1. الفكرة الجوهرية والمبدأ المعماري

نظام ماجد **ليس شات بوت**؛ هو **عملية مطابقة عقارية دقيقة** عليها قشرة محادثة. المحادثة هي الباب فقط، والقلب محرّك يطابق طلب المشتري مع المخزون، يرسل الخيارات، ويتابع — بأقل تدخل بشري.

**القرار المعماري الأهم: فصل المحادثة عن الحساب.**

- **HighLevel** يُشغّل ويخزّن: العملاء، المراحل (Pipelines)، الرسائل، والأتمتة (Workflows).
- **محرّك Cloudflare** يحسب: البحث، الفلترة، الترتيب، وتحويل العملة — بشكل ثابت وقابل للاختبار.
- **الذكاء الاصطناعي** للّغة والفهم فقط، **وممنوع أن يلمس أي رقم أو قرار مالي.** القاعدة الذهبية: **AI للّغة، لا للحساب.**

المبدأ التشغيلي: **HighLevel يشغّل ويربط · المحرّك يحسب · الإنسان يقرّر في المراحل الحساسة.**

## 2. نموذج البيانات (مصدر الحقيقة)

| الكائن (Object) | الدور |
|---|---|
| **Contact** | هوية الشخص وبيانات تواصله وخصائصه طويلة الأمد. **ليس** مصدر شروط المطابقة. |
| **Opportunity** | طلب المشتري المحدّد؛ **المصدر الرسمي لشروط المطابقة وحالة الرحلة**. |
| **Projects** | مشاريع الشركة: أنواع الوحدات، أسعار البداية، الأهلية، المرافق، المعلومات التسويقية. **مصدر البحث الافتراضي.** |
| **Property** | وحدة فعلية محددة أو عقار إعادة بيع (Resale) بسعر وتوفر ومواصفات خاصة. **مصدر البحث عند Resale فقط.** |

**العلاقات (Associations):**
- مشروع واحد ← عدة وحدات (Project 1 → Property N)
- الطلب ← المشاريع المطابقة (Opportunity ↔ Projects)
- المشروع ← جهات العرض (Project ↔ Broker / Owner / Agency / Developer)

**قاعدة الحقول الرسمية (Canonical):** لكل معلومة **حقل رسمي واحد فقط** تعتمد عليه الأتمتة. الحقول القديمة تُعامل Legacy ولا تُحذف قبل نسخ احتياطي والتأكد من عدم استخدامها. حقول `project_code` و`property_code` **فريدة** لمنع تكرار السجلات عند إرسال البروكر لنفس المشروع مرتين.

## 3. السستم كامل — بجملة واحدة

**جهتان تُغذّيان مخزوناً واحداً، ومحرّك واحد يطابق، وحلقتان تحافظان على المخزون طازجاً:**

```
          جهة العرض (تُدخل مخزون)                 جهة الطلب (مشترون)
   بروكر/مالك/وكالة/مطوّر يرسل عقارات         العميل يصل ويريد الشراء
                 │                                     │
            الاستقبال يصنّف ───────────────────── الاستقبال يصنّف
                 │                                     │
          وكيل الإدخال يحفظ                     وكيل المشترين يفهم
        Projects / Property                     ويحجز موعد ماجد
        + يربطها بالمورّد                              │
                 │                            ماجد يعبّي الاحتياجات
                 ▼                            وينقل إلى Active
        ┌──────────────────┐                          │
        │   المخـــــزون    │◄──────────────  محرّك المطابقة (Cloudflare)
        │  Projects/Property│                  دولار · أرخص 2 · ثابت
        └──────────────────┘                          │
                 ▲                            إرسال الخيارات وفق جدول
                 │                                     │
      حلقة تحقق 2 (دورية):                   حلقة تحقق 1 (عند اهتمام):
   كل فترة يعيد تأكيد المخزون          العميل يوافق → تريغر يراسل مصدر
   مع المصادر ويوقف القديم              العقار للتأكد من التوفر
                 │                                     │
                 └──────────── ماجد يغلق الصفقة ───────┘
```

**النتيجة:** كل عقار يدخل النظام مرة، ويُتأكَّد منه مرتين (عند اهتمام عميل به + دورياً)، والعميل لا يصله إلا عقار **موجود وسعره صحيح**.

## 4. جهة العرض — إدخال العقارات من المورّدين

عندما يرسل بروكر أو مالك أو وكالة أو مطوّر بيانات مشروع/عقار:

1. **الاستقبال** يصنّف المرسِل (`broker` / `owner` / `agency` / `Developer`) ويوجّهه لمسار الإدخال.
2. **وكيل الإدخال** يعامل المحادثة كـ**جلسة جمع معلومات**، لا كرسالة واحدة (البروكر قد يرسل التفاصيل على عدة رسائل).
3. لا يُنشئ سجلاً قبل إشارة اكتمال: البروكر يقول "خلصت"، أو Tag مثل `property-intake-ready`، أو تغيّر الموضوع.
4. يفصل بيانات **المشروع** عن بيانات **الوحدات**، ويتحقق من اكتمال الأساسيات، **ولا يخمّن** (لا العملة، لا المنطقة، لا اسم المشروع).
5. يبحث قبل الإنشاء (منع التكرار عبر `project_code`/`property_code`): إن وُجد يُحدّث، وإلا يُنشئ.
6. **يربط** كل Property بالمشروع الصحيح، ويربط المشروع بجهة العرض (المورّد) — لأن هذا المورّد هو من نراسله لاحقاً في حلقتَي التحقق.

**قواعد أمان الإدخال:** لا يحذف عقاراً أو مشروعاً · لا يحذف حقلاً · لا يغيّر بنية قاعدة البيانات · يوقف الإدخال ويطلب الناقص عند نقص البيانات.

## 5. جهة الطلب — رحلة المشتري

**بايبلاين المشترين (قلب النظام):**

| المرحلة | الوظيفة |
|---|---|
| Lead In | دخول العميل لمسار المشترين. |
| Call Done — Interests Filled | ماجد أتمّ المكالمة وملأ الاحتياجات في الـOpportunity. |
| **Active — Nurture Running** | **زر التشغيل** العملي للمطابقة والرعاية. |
| Unit Interest | العميل أبدى اهتماماً بخيار محدد. |
| Verifying with Owner | التحقق من التوفر مع جهة المشروع. |
| Viewing Scheduled | المعاينة والمتابعة البشرية. |
| Deal Closed | إغلاق الصفقة. |
| Lost | الخسارة — **لا يُنقل العميل إليها تلقائياً بمرور الزمن فقط**. |

**التسلسل:** العميل يصل ويُصنّف ← وكيل المشترين يفهم الطلب الأولي ويحجز موعد ماجد ← ماجد يعتمد الاحتياجات في الـOpportunity ← ينقلها إلى `Active — Nurture Running` ← المحرّك يطابق ← إرسال الخيارات وفق الجدول ← معالجة الرد.

**حقول طلب المشتري الرسمية (على الـOpportunity):**
`budget_max` · `budget_currency` · `property_location_interest` · `property_type` · `client_goal` · `property_source` · `sent_project_ids` · `rejected_project_ids`

## 6. محرّك المطابقة (Cloudflare — ثابت وقابل للاختبار)

خدمة حسابية صغيرة بين HighLevel وبيانات المخزون. لا تحتفظ بقاعدة عملاء مستقلة؛ تقرأ من HighLevel، تطبّق القواعد، تربط النتائج بالـOpportunity، وتعيد JSON منظّماً.

**تحديد مصدر البحث:**
- `property_source = Project` أو فارغ → البحث في **Projects** (المسار الأساسي).
- `property_source = Resale` → البحث في **Property** (السوق الثانوي).

**شروط قبول المشروع (بالترتيب):**
1. **المنطقة**: تبدأ المطابقة بالمنطقة الدقيقة المطلوبة.
2. **نوع الوحدة**: يجب توفّر النوع المطلوب (Studio / 1+1 / 2+1 / 3+1 / 4+1 / Villa / …).
3. **السعر بالدولار**: سعر بداية النوع المطلوب **بالدولار** ≤ `budget_max`. لكل نوع حقل سعر خاص:
   - `1+1` ← `price_1plus1_usd` · `2+1` ← `price_2plus1_usd` · Studio ← `price_studio_usd` … وهكذا.
4. **العملة**: المقارنة على قيمة موحّدة — الاعتماد الحالي **USD**.
5. **الأهلية**: الجنسية أو الإقامة تضيف شرط أهلية (مشاريع مؤهلة فقط). السكن والاستثمار لا يضيفان فلتر أهلية.
6. **عدم التكرار**: استبعاد `Sent Project IDs` و`Rejected Project IDs`.
7. **استبعاد الفارغ**: يُستبعد المشروع إذا كان سعر نوع الوحدة المطلوب **فارغاً**.

**المخرجات:** ترتيب من الأرخص إلى الأغلى ← اختيار **أرخص مشروعين** ← ربطهما بالـOpportunity **بشكل idempotent** (إعادة التشغيل لا تُكرّر الروابط) ← إعادة حالة: `MATCHED` / `NO_MATCH` / `RESALE_SKIPPED` / `ERROR`.

## 7. منطق المال

**توحيد العملة (TRY → USD):** المطابقة تقارن ميزانية العميل بسعر موحّد بالدولار. لذلك لكل سعر مصدر حقل USD موازٍ، مع حفظ السعر الأصلي وسعر الصرف ووقت التحديث (`usd_price_updated_at`, `exchange_rate_used`).

**خصم الكاش 15%:** **عرض تحفيزي في الرسالة فقط، وليس فلتر مطابقة.** إذا بدأ سعر المشروع من 200,000 دولار، تقارن المطابقة بـ200,000، ولا تعتبر مشروعاً أعلى من الميزانية مطابقاً بسبب الخصم. عند العرض: الكاش يُظهر السعر الأصلي وسعر الكاش بعد الخصم؛ التقسيط يُظهر السعر الأصلي وخطته دون خصم.

**الترتيب:** دائماً من الأرخص إلى الأغلى.

**هدف الشراء:**

| الهدف | القاعدة |
|---|---|
| سكن | لا شرط إضافي؛ المنطقة + النوع + الميزانية. |
| استثمار | لا شرط استبعاد إضافي؛ يُظهر العائد الإيجاري إن كان مسجلاً. |
| إقامة | مشاريع مؤهلة للإقامة فقط. |
| **جنسية** | مشاريع مؤهلة للجنسية فقط، **مع سقف 400,000 دولار (المجموع، لا عدد الوحدات)**. |

**قرار الجنسية المعتمد — خلط الأنواع مسموح:** عند هدف الجنسية، يُسمح للنظام **بتجميع أكثر من وحدة، ويجوز أن تكون من أنواع مختلفة** (مثلاً 1+1 مع 2+1)، للوصول إلى سقف 400,000 دولار — بشرط أن تكون الوحدات من مشاريع مؤهلة للجنسية. المحرّك يبني **تركيبة** تصل للحد المطلوب ويعرضها، بدل الاقتصار على وحدة واحدة.

## 8. حلقة التحقق 1 — عند اهتمام العميل (حدث)

عند موافقة العميل على خيار (الـOpportunity تنتقل إلى `Unit Interest`):

1. **تريغر أوتوماتيكي** يشتغل فوراً.
2. يقرأ **جهات العرض المرتبطة بالمشروع** عبر Associations (لا يُنشئ جهة جديدة).
3. يراسل **جهة واحدة فقط في كل مرة** للتأكد من التوفر.
4. إذا لم ترد خلال **6 ساعات** → ينتقل للجهة التالية المرتبطة.
5. عند تأكيد جهة → تتوقف مراسلة البقية، **يُشعَر ماجد**، ويُبلَغ العميل بالتأكيد.
6. إذا انتهت كل الجهات دون رد → يُشعَر ماجد، ويعود العميل إلى `Active` ويُرسَل له البديل التالي فوراً.

**النص المعتمد قبل البديل:** «الخيار السابق لم يعد متاحاً، لذلك جهّزنا لك بديلاً مناسباً.»

---

## 9. حلقة التحقق 2 — التحقق الدوري من المخزون (مجدول)

**وكيل مجدول** يعمل كل فترة على المشاريع/العقارات الموجودة:

1. يفحص العقارات التي لم يُؤكَّد توفّرها مؤخراً (اعتماداً على `Availability Checked At`).
2. يراسل **جهة العرض المرتبطة** ليؤكّد: هل العقار لا يزال متوفراً؟ هل السعر لا يزال صحيحاً؟
3. يحدّث التوفر والسعر عند الرد.
4. **يوقف أي عقار غير مؤكّد** حتى لا يُرسَل للعملاء.

**قاعدة نضارة التوفر:** خلال آخر 72 ساعة = توفّر حديث · أقدم من 72 ساعة = يحتاج إعادة تأكيد · لا يوجد تاريخ = غير مؤكد. لا يُقال «متوفر الآن» إلا إذا كانت البيانات حديثة فعلاً.

**قرارات مطلوبة لهذه الحلقة:** كل كم نراسل المصادر (مثلاً كل 3 أيام / أسبوعياً)؟ وعلى أي قناة (واتساب للمورّد)؟

## 10. محدّث الأسعار (أساس الصرف)

Worker مستقل يحوّل الأسعار إلى دولار ويملأ حقول USD:

- **مصدر سعر الصرف يجب أن يسمح بطلبات السيرفر** (Binance يحظر Cloudflare بـ403 — يُستبدل بمصدر مثل البنك المركزي التركي TCMB أو exchangerate.host).
- **TRY**: السعر بالدولار = السعر بالليرة ÷ سعر الصرف.
- **USD**: يُنسخ كما هو دون تحويل.
- تُحدَّث السجلات الفارغة أو التي مضى على تحديثها 48 ساعة فأكثر.
- يُقرَّب لأقرب دولار، ويُحفظ `exchange_rate_used` و`usd_price_updated_at`.
- **عند الخطأ لا يُمسح السعر السابق ولا يُكتب صفر** (فشل آمن).

> **تبعية حرجة:** المحرّك يطابق بالدولار؛ إن كانت حقول USD فارغة (بسبب فشل الصرف) فستكون المطابقة فارغة. لذلك يجب إثبات نجاح محدّث الأسعار **قبل** الاعتماد على المطابقة.

## 11. معمارية الـWorkflows

| Workflow | الوظيفة |
|---|---|
| **W1 — Buyer Matching Entry & Validation** | بوابة جودة: يبدأ عند `Active — Nurture Running`، يتحقق من اكتمال `budget_max`, `budget_currency`, `location_interest`, `property_type`, `client_goal`. إن نقصت البيانات يمنع المطابقة وينبّه ماجد؛ وإلا يوجّه إلى Projects أو Resale. |
| **W2 — Project Matching** | يرسل شروط الطلب للمحرّك عبر Webhook ويربط النتائج (أرخص 2). |
| **W3 — Options Delivery & Nurture** | يرسل الخيارات وفق الجدول، ويسجّل `Sent Project IDs`. |
| **W4 — Customer Response** | يوقف الرعاية عند أي رد، ويصنّف: رفض (يضيف لـRejected ويرسل التالي) أو اهتمام (ينقل إلى Unit Interest). |
| **W5 — Availability Verification** | يراسل جهات المشروع بالتتابع (واحدة كل مرة، 6 ساعات) — حلقة التحقق 1. |
| **W6 — Viewing & Human Handoff** | يوقف الأتمتة ويسلّم لماجد للمعاينة والتفاوض والإغلاق. |

**جدول إرسال الخيارات:**

| الوقت | ما يُرسل |
|---|---|
| اليوم 0 | أرخص خيارين مطابقين (أو خيار واحد إن لم يوجد غيره). |
| اليوم 3 | الخيار التالي الأرخص وغير المرسل. |
| اليوم 5 | الخيار التالي الأرخص وغير المرسل. |
| اليوم 7 | الخياران التاليان (أو واحد). |
| اليوم 14 · 21 · 28 | خيار واحد في كل موعد. |
| بعد الشهر الأول | خيار واحد كل 15 يوماً باستمرار. |

**قاعدة مهمة:** إن لم يوجد مشروع جديد في الموعد، **لا تُرسل رسالة فارغة ولا يُنقل العميل إلى Lost**؛ يبقى في `Active` ويعيد النظام البحث في الموعد التالي.

## 12. قواعد الأمان والحواجز (معايير القبول قبل النشر)

- لا تعمل المطابقة قبل انتقال الـOpportunity إلى `Active — Nurture Running`.
- لا تبدأ المطابقة إذا كانت الحقول الأساسية ناقصة.
- لا يُرسل مشروع أعلى من `Budget Max` بسبب خصم الكاش.
- لا يُعاد إرسال Project ID موجود في Sent أو Rejected.
- لا يُرسل أي نص فارغ عند عدم وجود نتائج.
- لا يُرسل W3 رسالتين متزامنتين لنفس الـOpportunity (قفل تنفيذ متزامن).
- أي رد من العميل يوقف الرعاية المجدولة قبل المعالجة.
- يُراسل مصدر عرض واحد فقط في كل لحظة.
- فشل الصرف أو HighLevel لا يمسح سعراً سابقاً ولا يكتب صفراً.
- **كل Workflow يبقى Draft حتى يمرّ باختبار تجريبي موثّق.**
- زر إيقاف (kill-switch) · إشعار لماجد عند أي فشل · إطلاق محدود 5–10 فرص مع مراقبة يومية.

## 13. ترتيب البناء من الصفر (لو الحساب فارغ)

**المبدأ الحاكم: من الأساس لفوق — البيانات أولاً، ثم الحساب، ثم المحرّك، ثم الأتمتة، وأخيراً المحادثة.** لأن أذكى وكيل يعطي نتائج خاطئة إذا كانت البيانات أو الحساب تحته خاطئة.

- **المرحلة 0 — قرارات على الورق:** الحقول الرسمية (Canonical، بلا تكرار)، منطق الجنسية (خلط الأنواع — محسوم)، جدول المناطق القريبة، مصدر سعر الصرف.
- **المرحلة 1 — نموذج البيانات:** إنشاء Projects وProperty وحقول Opportunity، أسعار الدولار من اليوم الأول، العلاقات، الحقول الفريدة.
- **المرحلة 2 — البايبلاينات:** مشترون، مورّدون، تأهيل.
- **المرحلة 3 — أساس الأسعار:** محدّث الصرف بمصدر موثوق، وإثبات عمله **قبل** أي مطابقة.
- **المرحلة 4 — محرّك المطابقة:** ثابت، دولار، أرخص 2، idempotent، مع اختبارات وحدة + تجربة حية.
- **المرحلة 5 — الوكلاء:** الاستقبال، وكيل المشترين، وكيل الإدخال (AI للّغة فقط).
- **المرحلة 6 — الـWorkflows:** W1 → W6.
- **المرحلة 7 — الأمان والاختبار:** Draft + kill-switch، اختبار end-to-end على حساب تجريبي، إطلاق محدود، توسّع تدريجي.

**لماذا يمنع هذا الأخطاء الحالية؟** الوضع الحالي بُني جزئياً بالمقلوب (المحرّك يطابق بالدولار قبل أن يُثبَّت أساس الأسعار)، فنتج «مطابقة بالدولار بلا أسعار دولار مضمونة». من الصفر، الأسعار تعمل قبل المحرّك، فلا يحدث هذا الخطأ.

## 14. القرارات

**محسومة:**
- الأساس = Project؛ Property للسوق الثانوي (Resale) فقط.
- الجنسية = **خلط الأنواع مسموح للوصول لسقف 400,000 دولار.**
- خصم الكاش 15% = عرض فقط، لا فلتر مطابقة.
- البشر: ماجد يعبّئ الاحتياجات ويشغّل، ويغلق الصفقة؛ وإشعارات عند الفشل/التأكيد.

**مفتوحة:**
- كيفية نقل نتيجة W2 إلى W3 (حفظ Option 1/2 في الـOpportunity أم استدعاء مباشر).
- جدول المناطق القريبة (مجموعات جوار محدّدة).
- مسار Resale: محرّك بحث مستقل داخل Property واختباره.
- محدّث الأسعار: مصدر صرف بديل عن Binance، ثم Dry Run → سجل واحد → تشغيل كامل → جدولة.
- الحلقة الدورية: التكرار (كل 3 أيام/أسبوعي) والقناة.
- إشارة "خلص الإدخال" للبروكر (Tag `property-intake-ready`).
